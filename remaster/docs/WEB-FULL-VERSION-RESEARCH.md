# Full game in the browser: research (19 Nov 2026)

Outranked by: `AI_stuff\standing\simon\botf-rulings.md` (19 Nov browser parity; 16 Nov hosting on Simon's site, low cost).

## Why the browser looks worse
Upstream Godot (4.5 and the current 4.7) exports to the web through WebGL 2 with the Compatibility renderer only. Forward+ and Mobile need WebGPU, which upstream Godot does not support on the web. So the browser loses glow, SSAO, volumetrics, SDFGI and full HDR. On top of that, we ship it lighter WebP textures.

## Options
| Option | Look | Cost | Risk |
|---|---|---|---|
| A. Polish WebGL (the parity pass now running) | Closer, still not full | Free | Low |
| B. Community WebGPU fork (Shane-Gadsby/godotwebgpu, MIT) | Full Forward+: glow, SSAO, SDFGI, volumetrics, TAA, FSR. 87/87 Forward+ tests pass in Chrome. | Free | Medium. One-person fork on Godot 4.8-dev (we are on 4.5); no known shipped game; Chrome/Edge solid, Firefox mostly, Safari untested; runs at about 45-75% of native speed |
| C. Cloud streaming (the PC renders, the browser gets video) | Exactly the desktop | GPU host about $250-380/mo, or tie up Simon's 4090 | Breaks the low-cost goal |

## Recommendation
Do B as a trial alongside A, and ship both builds: the page checks for WebGPU and loads the full Forward+ build, otherwise it falls back to the WebGL build. Trial steps:
1. Copy the project to a branch.
2. Upgrade it to the fork's 4.8 base.
3. Export with the fork's prebuilt templates.
4. Compare the same frames with the desktop.
5. Measure FPS and load size in Chrome, Edge and Firefox.
If the trial fails, A stands on its own.

## WebGPU trial round 3/r4 (19 Nov 2026, Barclay)
- Cause of the freeze, from Chrome traces: not WGSL translation alone. (1) The GPU process compiled 78 render pipelines synchronously (DXC, up to 3.9 s each) on the thread that also presents frames; (2) about 400 material shader stages that the export bake does not cover were translated SPIR-V to WGSL on the main thread (13-15 s).
- Fix 1, fork patch `remaster/tools/webgpu-fork/botf-async-all-and-wgsl-cache.patch` (on fork commit c4b5f43eb): every render pipeline goes through createRenderPipelineAsync while `globalThis.godotWebgpuAsyncAll` is not false, and pending draws are skipped. `godotWebgpuPending` counts what is still compiling. Compute is left out, because skipping one-shot compute work made hulls render black.
- Fix 2, shipped WGSL cache: WGSL recorded from play-throughs and keyed by SPIR-V hash goes in `wgsl-cache.js` (17.7 MB raw, 2.0 MB gzip). The driver checks it before translating, which took runtime translation from 402 stages to 0.
- Game: `webgpu_warm.gd` starts the off-screen battle warm-up on the galaxy screen and waits for pending to reach 0, then turns async-all off.
- Result: the shader stall is gone and the first battle's worst frame dropped from 12.6 s to 0.26-3.8 s. The 250 ms goal is NOT met. The frames still over it come from single-threaded main-thread loading (boot about 4.7 s, battle scene and hull setup about 3.4 s on a new profile). The shipped WebGL build has the same problem and worse: boot 17.9 s, battle 2.7 s.

## Round 5: shipped as two builds, loading spread over frames (19 Nov 2026, Barclay)
- Host folder `Documents\ChatGPT\BOTF-Web-Next\`: loader `index.html`, `webgpu\` (this branch, fork + async-all + `wgsl-cache.js`), `webgl\` (live tip), one shared `packs\` (pages set `globalThis.BOTF_PACKS='../packs/'`), `VERSION.txt`, `HOSTING.md`. Built by `BOTF-WebGPU-Trial\tools\assemble_next.py`; tested on a plain static host (no COOP/COEP, sub-path `/botf/`) by `tools\host_server.py` + `tools\host_run.py`, cold and returning profiles, through the loader.
- Game changes (live branch, cherry-picked here): web boot compiles the game's scripts a few per frame behind a "Starting" panel; App start-up one step a frame; hero glbs load a step per frame (parse, scene, one image's mips per step, plating, pack) because the web has no worker threads (ResourceLoader threaded loads run inline there); title backdrop a piece per frame; `LOADT` console trace of any loading step of 20 ms or more.
- Result (Chrome, worst frame): boot 4.3 s -> 2.2 s; returning-profile battle open 2.6 s -> 1.0 s; cold battle open and round 1 stay under 250 ms. 250 ms everywhere is NOT met. What is left, from the trace: engine start before any game code (about 2 s), GPU-process pipeline compiles while the title first draws (1.2-2 s frames with no game code running), procedural lead hull material creation on WebGPU (1.4 s, shader compile in wasm), the GLTF parse of a big hull (`append_from_file` decodes every embedded image: up to 1 s) and the first galaxy plus battle warm-up (1.5-1.9 s). On WebGL (Firefox) the first draw still freezes 12-15 s for ANGLE shader compiles; returning visits do not cache them in Firefox.
- Next steps: parse glbs with textures discarded and decode them per frame ourselves (halves the parse and removes the double decode); bake the remaining material shaders so wasm never runs glslang at runtime; warm hulls when their packs mount on the galaxy.

## Round 7: freezes from shaders, script compile, shader pack size and audio (19 Nov 2026, Barclay)
- Runtime materials still compiling (step 1): a `--verbose` copy of the web build printed every `Shader cache miss`: 7 misses, 4 ParticleProcessMaterials and 3 StandardMaterial3Ds, all from `BattleFx.prewarm()` bursts (the title's background battle warm-up) and a damaged ship's fire/smoke/vent emitters (`BattleShip._particle_mat`). The capture tool sampled the tree every 15 frames and prewarm frees its bursts after 3, so they were never saved and never baked. It now collects every frame and adds every `_particle_mat` combination: 17 materials (was 6); the verbose run shows 0 misses.
- Boot script compile (step 2): `main.gd` named `ShaderWarm`, which named the battle scripts, so engine start compiled them before the Starting panel. ShaderWarm is now loaded by path. The boot compiles scripts leaves-first (`scripts/boot_order.gd` from `remaster/tools/web/gen_boot_order.py`). That alone only moved the 450-550 ms frame from galaxy_map.gd to the first script of a 32-script reference cycle (App, the battle scripts, the audio autoload). A CPU profile showed about 30% of every compile frame was Emscripten file-system path lookups for res:// files that are not there (.remap, .import probes), each a JS exception. Fork patch `remaster/tools/webgpu-fork/botf-r7-web-res-miss-cache.patch` remembers missing res:// paths (exported web only). The largest boot compile is now 184-296 ms (was 507-637).
- Shader pack (step 3): 106-111 MB was 70% Forward+'s advanced group (motion vectors, TAA, FSR 2), baked because the baker's scan found the word `scaling_3d_mode` in display_settings.gd (it sets FSR 1 only). The property is set by a built name now. The export moves the advanced group to `index.shaders_extra.bin` (86 MB, fetched during load). The game never turns those passes on, so the host folder leaves the extras out (`BOTF-WebGPU-Trial\r7\tools\drop_extras.py`; the file is kept in `r7\extras-s4`). Shader pack: 25.4 MB. No runtime warnings about unbaked groups.
- Edge round-1 voice-line freeze (step 4): seen as a 4.5-5.2 s frame starting about 0.2 s after RESOLVE ROUND, ending just before the first Voice-bus sound (r6 Edge, r7 step-1 Chrome). It has not come back in 18 runs since step 1 was finished (6 profiled hunt runs included), so it most likely came from the round-time material compile that step 1 removed. Separately, music and voice now use Stream playback on the web: as Samples the title track was decoded whole on the main thread (about a 2 s frame on returning visits).
- Not met: no frame over 250 ms. What is left (Chrome/Edge, RTX 4090): engine start before game code (0.7-1.1 s, two frames); GPU-process pipeline compiles while ShaderWarm draws (0.5-1.0 s frames with no game code running); saving downloaded packs to IndexedDB (`FS.syncfs`, 0.8-2.3 s, worst with the 46 MB planets_hi pack); a 0.3-0.7 s JS garbage collection during warm-up. Next steps: keep packs in the Cache API from the service worker instead of IndexedDB through the Emscripten file system; split engine start; ship the Dawn pipeline cache warm-up later or behind the title.

## Round 8: pack storage, galaxy pipelines, HTML loading screen, GC (19 Nov 2026, Barclay)
- Test change first: the driver now waits for a `BOTF title up` console line, printed once Preparing graphics is over and the title has drawn (r7 shot the Edge returning title while Preparing graphics still showed). Baseline r0 = the r7 release re-run under the new wait: worst frame Chrome 1.46 s cold / 2.14 s returning, Edge 2.32 s / 2.40 s.
- Pack storage (step 1): fetched packs live in an in-memory folder outside user:// (`/botf-packs/`) and persist in the Cache API (`botf-packs`, keyed by URL, the cache web-host/sw.js already uses), written by the browser off the page's thread. Nothing goes to IndexedDB any more; copies an older build saved in user://packs still mount. The `flush to IndexedDB` frames are gone. The worst frame did not move (2.0-2.4 s): a trace showed the remaining one was the GPU process compiling particle compute pipelines (below), which had sat next to the flushes.
- Galaxy pipelines (step 2): ShaderWarm now also draws a GalaxyMap built from the shipped campaign-view fixture (whole disc, then a system close-up) in an off-screen viewport with the window's MSAA, behind the boot panel; the battle warm-up starts a second after the galaxy opens instead of in its first frame. Galaxy open: 0.27-0.35 s (r0 Edge returning: 2.4 s). The trace also showed every Preparing graphics freeze (0.5-0.9 s each) and the 2 s post-title freeze were synchronous `createComputePipeline` calls for ParticlesShaderRD on the GPU process's main thread (DXC, 0.55-0.72 s each). Fork patch (template rebuilt, `BOTF-WebGPU-Trial\r8\fork-particles-async.txt`): particle compute pipelines always compile through createComputePipelineAsync and their dispatch is skipped until ready; other compute stays synchronous. Returning-visit boot worst: 2.0-2.3 s -> 0.69 s.
- HTML loading screen (step 3): the export's head_include adds a plain HTML screen with a CSS spinner over the canvas from first paint; main.gd mirrors the boot text to it and removes it two frames after the title screen exists. Engine start (two frames of 0.6-0.8 s) and Preparing graphics now happen behind it. These are still long frames for the page: the spinner is a compositor animation and keeps turning, but the main thread is busy. Reported separately below as "hidden".
- GC (step 4): pack bytes are read into one buffer of the manifest's size (was: chunks plus a concatenated copy) and handed to the in-memory file system without a copy (`FS.writeFile(..., {canOwn: true})`). CPU profiles: after the title no GC pause over 100 ms (r7: 0.2-0.5 s at the pack loads). A 0.6-0.8 s GC remains during the shader warm-up on cold visits (shader-module text crossing wasm to JS), behind the HTML screen.
- Fix found while measuring: a fixture hull whose pack landed after the battle warm-up began was parsed whole in its first round (2.6-3.0 s at galaxy open). The warm-up now queues such hulls a step per frame first.
- Result (s5, RTX 4090): shown (after the HTML screen): Chrome 0.64 s cold / 0.30 s returning, Edge 0.31 s / 0.35 s. Hidden (engine start, Preparing graphics): 0.75-1.88 s. 250 ms is NOT met. What is left in the shown part: the Tactical-drill click that starts the session and builds the galaxy plus its first draw (0.26-0.37 s), the off-screen battle view being built a second later (0.27-0.35 s), pack mounts after the title (0.26-0.64 s, not in GDScript), and a hull's `generate_scene` step (0.23 s).
