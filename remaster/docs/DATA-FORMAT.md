## 2. Files

Authoring layout (one folder per pack):

```
remaster/data/
  base/                    the vanilla-plus-remaster pack (authoring source, hand-editable)
    pack.json              id, name, format, section file list
    technologies.json  ships.json  buildings.json  races.json  roster.json  minors.json  events.json
  base.pack.json           GENERATED bundle: every section merged, canonical bytes (section 3)
```

- The **bundle** (`*.pack.json`) is the only thing the core reads. It is one JSON object, so a host hands it over as one byte buffer.
- `tools/content/build_pack.py` validates `data/base/`, writes `data/base.pack.json` and regenerates `game/Source/BotfSim/ContentBase.generated.h` (the bundle embedded as string chunks). Run it after any data edit; `--check` exits 1 if any output is stale. ContentTests separately fails if the embedded header and `data/base.pack.json` differ (section 8).
- `tools/ship_roster/gen_ship_roster.py` stays the source of truth for the expanded roster: it now writes `data/base/roster.json` (previously `ShipRosterData.h`); run `build_pack.py` after it.
- `tools/content/export_from_headers.cpp` is the one-time migration exporter (compiled against the pre-M0 headers at f2581a7). It is kept for provenance and the field-by-field equality proof (section 9); it is not part of the build.

## 3. Bundle and canonical form

```json
{"format":1,"id":"botf-base","name":"BOTF Remastered base content","revision":1,
 "technologies":[...],"ships":[...],"buildings":[...],"races":[...],"roster":[...],"minors":[...],"events":[...]}
```

- `format` is the data-format version; the core accepts exactly `1` (`content::FormatVersion`). A future format bump adds a migration in the loader, the same pattern as save schemas (`Simulation.cpp` `deserialize`, legacy7..legacy13).
- `id`: `[a-z0-9-]{1,40}`. `botf-base` is reserved for the embedded base pack.
- Canonical bytes, as written by `build_pack.py`: UTF-8 without BOM, non-ASCII written raw (no `\u` escapes); the four pack keys on the first line; then each section as `"name":[` on its own line, one record per line (keys in the order section 4 lists, separators `,` and `:` with no spaces), then `]`; `\n` line ends; the document ends with `}` and a newline. Numbers are integers except the ship fields `range` and `speed` (section 4).
- `data/.gitattributes` marks `*.json` as `-text`, so a Windows checkout with `core.autocrlf=true` cannot turn `\n` into `\r\n` and change the checksum.
- The core does **not** re-canonicalise: the checksum is over the exact bytes it was handed. Two packs that differ only in whitespace have different checksums. Always ship the bundle `build_pack.py` wrote.

## 4. Sections and records

Every array is ordered and every record carries its id. Ids are save data: never renumber or reuse one.

**technologies**: `{"id","name","field","level","cost","description"}`. Rule: `id == index`, `field == id / 11`, `level == id % 11` (the core indexes `TechnologyCatalogue[field * 11 + level]`, `Simulation.cpp:3639`). Exactly 77 records (7 fields x 11 levels). `cost` is a 64-bit integer.

**ships** (legacy catalogue): `{"id","raceId","name","shipClass","technologyRequirements":[6],"industryCost","maintenance","hull","shields","attack","range","speed","role","troopCapacity","description"}`. Rule: `id == index`, count below 1000 (`roster::ExpandedIdBase`). `technologyRequirements` order: Biotech, Computers, Construction, Energy, Propulsion, Weapons. `range` and `speed` are decimals (section 5).

**buildings**: `{"id","name","technologyField","technologyLevel","industryCost","energyCost","populationCost","moraleBonus","excludedEmpireMask","residentRaceMask","bonusType","bonusValues":[6],"unrestBonuses":[6],"description"}`. Rule: `id == index`. `residentRaceMask` is an unsigned 64-bit integer, read exactly (never through a double).

**races**: `{"id","name","icon"}`. Rule: `id == index`.

**roster** (expanded ships): `{"id","assetKey","faction","raceId","minorRaceId","roleName","className","hullRole","engineRole","era","tier","technologyRequirements":[6],"industryCost","buildTurns","maintenance","hull","shields","attack","torpedoSharePercent","weapons":[{"type","count","arc"} x4],"weaponCount","speed","range","sensors","cloak","sourceKind","source","buildable","description","flight":{"turnRate","acceleration","lateral","size"}}`. Rules: ids strictly ascending inside [1000, 2000) (was `static_assert`, `ShipRoster.h:50`); `weapons` has exactly 4 mounts, unused mounts are `{"type":"None","count":0,"arc":"Forward"}`; `cloak` and `buildable` are JSON booleans. Enum fields are strings naming the C++ enumerator: `faction` (`Faction`), `hullRole`, `era`, `sourceKind`, weapon `type` (`WeaponType`), `arc` (`FiringArc`), `flight.size` (`SizeClass`), all in `ShipRosterTypes.h`.

**minors**: `{"id","name","homeworld","referenceRaceId","temperament","techLevel","population","bonus","bonusValue","signatureShipId","affinity":[6],"description"}`. Rules: `id == index + 1`; `temperament` names `minors::Temperament`, `bonus` names `minors::JoinBonus`; `affinity` values in -2..+2. `MinorRaceCount` is now the loaded roster size.

**events**: `{"kind","name","defaultChoice","choices":[{"label","effect"}],"description"}`. Rules: exactly 7 records in `GalacticEventKind` order (`Plague, SupernovaWarning, SubspaceRift, TradeBoom, DerelictVessel, LaborUnrest, ScientificBreakthrough`); the five choice kinds (`eventHasChoice`, `GalacticEvents.cpp:18`) carry exactly 3 choices and a `defaultChoice` in 0..2, the others carry none and `defaultChoice` -1 (the save validator checks choice indices against these counts, `GalacticEvents.cpp:73`). `description` is a template: `{where}`, `{magnitude}` and `{endTurn}` are replaced at run time; no other `{` is allowed.

Text fields are original remaster text. `ContentTests` still hashes every description sentence against the original game's prose (`ContentTests.cpp:43`), now over the loaded data.

## 5. Numbers and determinism

- The loader has its own JSON reader (`ContentJson.h`): no `strtod`, no locale, no `from_chars` for floats, so native MSVC, Emscripten and mingw read identical values.
- Integers are parsed exactly into `int64`/`uint64` with overflow checks, then range-checked into the field type.
- Decimals (`range`, `speed` only): at most 15 significant digits and 15 fraction digits, no exponent. The value is `mantissa / 10^k` computed in one IEEE division of two exactly representable doubles, which is correctly rounded on every IEEE platform.
- Loading never draws from the campaign RNG and never depends on time, so a pack is a pure function of its bytes.

## 6. Loading: the host hands bytes, the core never opens files

Browser target (M0-LANES "Browser target": "No disk paths at runtime"): the core has no file I/O for content.

```cpp
namespace botf::content {
const PackInfo& install(std::string_view bundleBytes); // parse + validate; atomic: on any error the active pack is unchanged and std::runtime_error names the section, record and field
const PackInfo& installBase();                         // the embedded base pack (ContentBase.generated.h)
const PackInfo& active();                              // installs the base pack on first use
std::uint64_t baseChecksum();
std::string checksumHex(std::uint64_t);                // 16 lowercase hex digits
}
```

- **Default.** If the host installs nothing, the first table access installs the embedded base pack. Native tests, the web client's WASM core and Unreal need no change.
- **Godot (desktop and web).** Godot reads `res://data/<pack>.pack.json` with `FileAccess.get_file_as_bytes` (works inside a `.pck` and on web) and passes the bytes to the core through one bridge call. The bridge call is in `web/bridge/WebBridge.cpp`, which lane L5 does not own; the exact addition needed is in section 10.
- **Lifetime.** Records point into strings owned by the pack. A replaced pack is kept alive until exit, so pointers a caller already holds stay valid. Packs are small (the base bundle is under 1 MB).
- **When.** Install before `newCampaign` or `deserialize`. Changing the pack mid-campaign is the host's job to prevent; loading a save checks it (section 7).

## 7. Where the content checksum lives

Decided before code, so the format does not change halfway:

- **Checksum:** 64-bit FNV-1a over the bundle bytes (the same `hashText` the save checksum uses, `Simulation.cpp:76`), shown as 16 hex digits.
- **In the save and the fingerprint: one optional section, `CONTENT <id> <checksum-hex>`**, the last section before `CHECKSUM`. `fingerprint()` hashes `payload()` (`Simulation.cpp:5551`), so the line is inside the determinism fingerprint by construction.
- **Written only when the active pack is not the base pack.** This follows the existing rule for optional sections ("so every save without the roster keeps its exact previous text", `Simulation.cpp:3172-3174`). Consequences:
  - Base-content saves and fingerprints are byte-identical to before M0, so every committed fixture, every existing save and the WASM-recorded `godot/fixtures/determinism.json` (checked by `test_fixture_determinism`, `godot/tests/run_tests.gd:196`) still match without rebuilding the WASM.
  - A modded campaign carries its pack id and checksum in every save and its fingerprint; two peers on different packs produce different fingerprints (private multiplayer, MASTER-PLAN §7).
- **Load rule (strict, because a save replayed on other data diverges):**
  - save has `CONTENT id sum`: the active pack's checksum must equal `sum`, else `Save needs content pack <id> (<sum>); active pack is <id> (<sum>)`;
  - save has no `CONTENT`: the active pack must be the base pack, else `Save was made with the base content pack; active pack is <id>`.
- **Migration.** None needed: the schema stays 14 (`Simulation.h:22`) and `CONTENT` is optional. Legacy saves (schemas 4-13) have no `CONTENT` and load under the base pack as before.
- **Balance edits to the base pack** change `baseChecksum()` but not base saves (no line is written). That matches today, where a header edit silently changed a rebuilt core. Fixtures that record numbers derived from content must be re-recorded after such an edit, as before.

## 8. Validation and tests

The loader rejects: unknown or missing keys, wrong types, out-of-range integers, broken id rules (section 4), duplicate roster ids, unknown enum names, a legacy ship count at or above 1000, a minor whose `referenceRaceId` or `signatureShipId` points outside the loaded tables, and event templates with unknown placeholders. Errors name the path, e.g. `content: roster[12].weapons[2].type: unknown WeaponType "Phasor"`.

`BotfContentTests` (`tests/scenarios/ContentTests.cpp`) adds:
- the embedded bundle equals `data/base.pack.json` byte for byte, and its checksum is reported;
- installing a modified pack changes `ShipCatalogue` values, writes `CONTENT` into the save, changes the fingerprint, and that save refuses to load under the base pack;
- a base save refuses to load under a mod pack, and loads again after `installBase()`;
- malformed packs are rejected with the active pack unchanged.
